Maintain SQLite as the client interaction store and the Durable Object as the

## Concrete deliverables

### 1. Versioned content-addressed chunk contract

Define hashes, canonical bytes, MIME/encoding metadata, size limits, and a
versioned manifest. Hashes must be verified from received bytes, not trusted
from filenames or clients. Define chunk-reference operations/capabilities and
regenerate all schemas and fixtures through the repository generator.

Do not truncate oversized operations. Reject unknown algorithms, invalid
manifests, missing chunks, inconsistent lengths, hash mismatches, and payloads
above configured limits with stable errors.

### 2. Authorized resumable R2 transfer

Implement upload, existence/deduplication, retrieval, and cleanup through
authenticated workspace-authorized routes. Bound concurrency, memory, request
sizes, and retry behavior. Prevent cross-workspace probing even when two
workspaces contain identical bytes. Document whether physical deduplication is
global or workspace-scoped and how authorization remains enforced.

Interrupted uploads must resume or restart safely without publishing an
operation that references unavailable content. Orphan cleanup must never delete
a chunk reachable from a retained operation, checkpoint, conflict, or recovery
artifact.

### 3. Versioned checkpoint format

Define a checkpoint containing a validated canonical workspace snapshot,
checkpoint server sequence, referenced chunk manifest, protocol/schema version,
and integrity metadata. Reuse canonical archive/domain contracts where suitable
instead of inventing a second document model, but do not weaken archive
validation or copy raw SQLite files.

Checkpoint publication must be atomic from a client's perspective: incomplete
artifacts are never discoverable as current. A hydrating client verifies all
metadata and content before replacing/initializing local canonical state, then
pulls the ordered tail strictly after the checkpoint sequence.

### 4. Retention and compaction

Persist per-device acknowledgement/checkpoint cursors. Specify inactive-device
expiry and recovery policy. Compact log entries and unreferenced chunks only
when retained checkpoints, active device cursors, tombstones, and unresolved
conflicts make deletion safe.

### 5. Tests and operational documentation

Test:

- upload retry, duplicate chunks, hash collision/mismatch simulation, partial
  upload, missing chunk, unauthorized access, and oversized content;
- checkpoint creation interruption and atomic publication;
- hydrate fresh device from checkpoint plus tail;
- duplicate and concurrent checkpoint builders;
- stale device recovery and bounded replay;
- compaction with active/stale devices, tombstones, conflicts, and orphan data;
- archive/domain validation rejecting corrupt hydration state;
- memory and latency bounds with representative large workspaces.

Document R2 bindings, retention policy, quotas, observability without content,
backup/recovery, deletion, and incident procedures.

## Non-goals

- No raw SQLite/page upload.
- No public unauthenticated object URLs.
- No client-trusted hashes or unbounded replay.
- No automatic conflict winner hidden inside checkpoint generation.
- No deploy, commit, push, or real credentials.

## Done condition

An authorized new device can hydrate a representative large workspace from one
verified checkpoint plus a bounded ordered tail. Oversized supported content
syncs without truncation, interrupted transfers recover safely, cross-workspace
access fails, and tested compaction cannot remove data needed by active devices,
tombstones, conflicts, checkpoints, or recovery.
