# Agent 4 — Specify and implement sync convergence and conflict recovery

Work in `/home/remcostoeten/dev/skriuw`, follow `AGENTS.md`, preserve the dirty
tree, and keep all work in v2. Do not touch legacy products or unrelated files.

## Objective

Turn ordered delivery into deterministic product behavior for every replicated
operation family. Define when remote operations can apply directly, when they
must transform against concurrent work, and when Skriuw must preserve both
versions for explicit user resolution.

Server sequence is delivery order, not a merge algorithm. No user content may
be silently discarded merely because one operation arrived later.

operation match.

## Phasing requirement

First publish the merge matrix and executable scenario tests. Only then modify
domain or storage behavior. If a product decision remains ambiguous, preserve
both outcomes in a conflict rather than inventing destructive last-write-wins.

## Concrete deliverables

### 1. Exhaustive merge matrix

For every replicated operation variant, specify:

- identity and dependency requirements;
- commutative, ordered, transformable, or conflicting behavior;
- same-field and different-field concurrent edits;
- delete/trash/restore/purge versus edit or move;
- missing-parent, missing-note, and reused-identity outcomes;
- retry and duplicate behavior;
- history, archive, and user-recovery implications.

Use stable conflict classes. Distinguish protocol-invalid input, unavailable
dependency, revision conflict, identity conflict, and intentionally preserved
concurrent versions.

### 2. Safe reconciliation boundary

Implement the smallest domain-level reconciliation API that stays independent
of SQLite, Tauri, networking, and operating systems. Keep persistence and
transport adapters outside it. Do not create a universal merge framework when
explicit operation-family logic is clearer.

Document operations that can apply unchanged, operations requiring a
deterministic transform, and operations that must produce a recovery artifact.

### 3. Document conflict preservation

For unsafe concurrent document edits, preserve both complete versions with
their origin operation/device/revision metadata. Define a resolution operation
or explicit storage use case that records the user's choice without erasing the
unselected version from recoverable history.

Specify renderer-facing conflict summaries and accessible resolution actions,
but keep retry/cursor policy out of React state. If UI implementation is too
broad for this task, deliver the typed public contract and behavior tests and
state that boundary clearly.

### 4. Tombstones and structural safety

Define tombstone creation and retention for trash, purge, and delete-like
operations. A delayed edit or stale checkpoint must not resurrect purged
content. Tie safe deletion of tombstones to retained device cursors and
checkpoints, not wall-clock time alone.

Cover folder/note movement, cycles, missing anchors, concurrent reordering,
parent deletion, restore destinations, properties, templates, and attachments.

### 5. Fault and property tests

Generate or enumerate two-device histories and replay them with:

- duplicate and reordered delivery;
- two offline writers;
- clock skew;
- restart between record/apply/resolve stages;
- edit-versus-edit, delete-versus-edit, move-versus-move, and restore conflicts;
- delayed operations after tombstone/checkpoint boundaries;
- archive export/import with unresolved and resolved conflicts.

Assert deterministic results independent of delivery batching, no silent
content loss, no invalid tree, idempotent replay, and durable recovery after
restart.

## Non-goals

- Do not implement auth, transport, chunks, checkpoints, or browser OPFS.
- Do not use timestamps as a universal conflict winner.
- Do not purge conflict evidence merely because the cursor advances.
- Do not broaden React context with transient editor or sync state.
- Do not deploy, commit, or push.

## Done condition

Every replicated operation has a documented and tested concurrent outcome.
Unsafe document conflicts preserve both versions, deleted content cannot be
incorrectly resurrected, replay is deterministic and idempotent, and unresolved
conflicts survive restart and archive/recovery flows according to the published
contract.
