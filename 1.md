## Deliverables

### 1. Durable operation-policy specification

Create a canonical specification under `v2/docs/specs/` that inventories every
current `WorkspaceOperation` variant.

For every operation, document:

- its replication class: replicated workspace content, device-local state, or
  unsupported by sync protocol v1;
- ordering requirements;
- conflict or merge behavior;
- tombstone/deletion implications;
- whether it contains large document or media content;
- whether inline v1 transport is sufficient or chunk transport is required;
- recovery-visible or user-visible failure implications.

Make deliberate decisions for ambiguous operations such as `SetActiveNote`,
`UpdateSettings`, `RecordProviderImport`, `CreateNote`, `SaveDocument`,
`AttachImage`, trash/restore/purge, and property-template operations. Do not
classify an operation as replicated merely because it serializes.

### 2. Explicit Rust domain policy

Add the smallest suitable domain API for determining whether an operation is:

- replicated in sync protocol v1;
- device-local; or
- unsupported until a later protocol capability/version.

The Rust domain is the canonical source of protocol rules and must remain free
from database, filesystem, framework, network, and operating-system concerns.
Prefer an exhaustive match so a new `WorkspaceOperation` requires an explicit
policy decision. Avoid a generic registry or broad abstraction.

Only add a capability or policy-version field to the sync envelope if it is
concretely necessary. If wire types change, regenerate schemas and update
fixtures through the repository generator rather than editing schemas by hand.

### 3. Trust-boundary enforcement

A device-local or unsupported operation must not be silently accepted into the
cloud ordered log. Reject it with a stable, actionable error classification,
not only an arbitrary message string.

Preserve the current safety posture:

- `/health` may remain available;
- public `/v1/*` routes remain disabled;
- do not add authentication or expose public synchronization;
- do not weaken size, identifier, version, sequence, idempotency, or workspace
  isolation checks;
- do not truncate large operations;
- do not mistake server ordering for a merge algorithm.

Rust remains canonical. Avoid an unconstrained second policy source in
handwritten TypeScript. Use generated contracts/fixtures or the smallest
drift-checked representation suitable for the Worker.

### 4. Tests

Test through public domain and Worker interfaces. At minimum, prove:

- every current `WorkspaceOperation` has an explicit policy;
- representative replicated operations are accepted;
- device-local operations are rejected from replication;
- protocol-v1 unsupported operations return the correct stable error;
- a new operation cannot accidentally default to replicated;
- the golden fixture remains valid;
- malformed envelopes and unknown operation types are rejected;
- retry, duplicate ID, conflicting duplicate, client-sequence, pull-order, and
  workspace-isolation behavior remains passing.

### 5. Documentation status

Link the policy specification from the cloud tracker and ADR where useful.
Update a checkbox in `v2/docs/specs/cloud-sync-master.md` only when code and
tests genuinely satisfy it. Link canonical documentation instead of copying
